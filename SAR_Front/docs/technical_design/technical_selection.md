# 大体积TIFF文件缩略图生成技术选型对比文档

## 1. 方案概述

针对大体积TIFF文件（单张100MB-500MB，甚至GB级）无法在前端直接预览的问题，我们设计了两套技术方案：
1.  **纯前端方案**：利用浏览器计算能力（WebAssembly/Web Worker）在客户端完成解码与缩略图生成。
2.  **后端分离式方案**：利用服务器高性能计算资源（Python/GDAL）进行异步处理，生成Web友好的图片格式。

## 2. 方案详细对比

| 维度 | 方案一：纯前端 (WebAssembly/JS) | 方案二：后端分离式 (Python/GDAL) |
| :--- | :--- | :--- |
| **核心技术** | `geotiff.js` / `libtiff-wasm` + Web Worker + Canvas + IndexedDB | Python, FastAPI, Celery, Redis, GDAL, Pillow-SIMD |
| **处理位置** | 客户端浏览器 | 服务端集群 |
| **网络开销** | **低**。仅需读取文件部分数据（Range请求）或本地文件API，无需全量上传即可尝试渲染（流式）。但若需上传原图，则耗时相同。 | **高**。必须先上传完整文件到服务器（或对象存储），然后下载缩略图。 |
| **计算资源** | 依赖用户设备性能（CPU/内存）。低端设备可能卡顿或崩溃。 | 依赖服务器资源。可横向扩展，性能稳定可控。 |
| **响应速度** | 小文件快（无上传等待）。大文件受限于JS/WASM解码速度，可能较慢。 | 取决于上传速度 + 队列排队时间 + 处理时间。通常用于异步展示。 |
| **支持格式** | 受限于JS库支持。部分复杂压缩（如JPEG2000, LZW复杂变种）可能支持不完善。 | **全**。GDAL库支持几乎所有TIFF变种和投影信息。 |
| **内存占用** | 浏览器限制严格（通常单标签页1-4GB，但大对象分配易失败）。需精细管理内存（分片）。 | 服务器内存充足，可处理超大图像（GB级）。 |
| **实现复杂度** | 中高。需处理Web Worker通信、内存管理、OffscreenCanvas兼容性。 | 中。成熟的微服务架构，但需维护额外基础设施（Redis, Celery）。 |
| **适用场景** | 用户设备性能较好、网络带宽有限、需即时预览、数据隐私要求高（不上传）。 | 文件超大（>500MB）、需高质量重采样、需生成多级金字塔瓦片、批量处理。 |

## 3. 技术选型分析

### 3.1 前端方案选型
*   **解码库**：
    *   **`geotiff.js`** (推荐)：纯JS实现，支持多种压缩格式，生态活跃，已在项目中使用。支持读取特定区域（Window），适合生成缩略图。
    *   `utif.js`: 轻量级，但对GeoTIFF支持不如geotiff.js全面。
    *   `libtiff-wasm`: 基于LibTIFF编译，性能强，但集成复杂，包体积大。
*   **并行处理**：**Web Worker**。必须使用，避免阻塞UI主线程。
*   **缓存策略**：**IndexedDB**。LocalStorage容量太小（5MB），不适合存图片。IndexedDB支持存储Blob，容量大。

### 3.2 后端方案选型
*   **Web框架**：**FastAPI**。高性能异步框架，原生支持并发，适合IO密集型任务。
*   **任务队列**：**Celery + Redis**。成熟的分布式任务队列解决方案，支持任务重试、定时任务、监控。
*   **图像处理**：
    *   **GDAL**: 处理GeoTIFF的行业标准，保留地理信息，支持所有格式。
    *   **Pillow-SIMD**: Pillow的高性能分支，利用AVX2指令集加速Resize操作。
    *   **pyvips**: 内存占用极低，适合处理超大图片（流式处理），作为GDAL的补充。

## 4. 性能指标预期

### 前端方案
*   **100MB TIFF**: < 3秒 (依托Web Worker多线程)
*   **内存峰值**: < 200MB (通过分片读取和Canvas流式处理)
*   **最大支持**: 500MB (受限于浏览器最大ArrayBuffer分配)

### 后端方案
*   **1GB TIFF**: < 10秒 (纯处理时间，不含上传)
*   **并发能力**: 可通过增加Worker节点线性扩展。
*   **压缩比**: WebP格式可将原图压缩至1%以下作为缩略图。

## 5. 结论

**建议采用混合策略**：
1.  **优先前端生成**：用户选择文件后，立即尝试在前端生成低质量预览图（快速反馈）。
2.  **后端异步处理**：文件上传后，后端生成高质量、多尺寸的缩略图/瓦片，并更新前端展示。
3.  **降级策略**：若前端解码失败（格式不支持或内存不足），自动回退到显示默认图标，等待后端处理完成。
